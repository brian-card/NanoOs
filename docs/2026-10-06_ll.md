# 6-Oct-2026 - `ll`

This update is to be remembered for two things:
- This is the point at which my OS started *looking like* Unix
- This is the point at which I finally...  **FINALLY**...  got asynchronous RX from UARTs working

After a few times of breaking main this round, this may also be remembered as the point at which I started doing proper branching.  All development work now happpens on the `dev` branch and is only merged to `main` after it's confirmed working on all targets.

First, to recap, the goal of NanoOs's userspace has always been to be Unix-like.  I was starting to have trouble remembering everything on the filesystem and was getting annoyed that I had no way to find out from the OS, so I figured it was time to put together a real `ls` command.  Now, my goal was not to support all options of the command.  I really just wanted the output of `ls -al`.

The first thing I needed for this was proper `dirent.h` support.  That's standard POSIX functionality on top of FAT32, so Claude to the rescue on that one.  That much got me the output of a basis `ls`.  I've never implemented this command before, so I then started tracking down what I needed to get the rest of the output.  It turned out that the answer was the `lstat` call, so, with a little more work from Claude, I implemented that as well.

And...  I hated it.  For the most part it was fine, but on the Agon Light 2, which is my main target these days, it was abysmally slow.  One of the main problems was that `lstat` takes the path to a filename, which means that, for each file, I first had to construct the full path to the filename in dynamic memory, then walk the directory structure until I found the file, and THEN populate a `stat` structure.  That's a lot of system calls and seemed like a waste to me.

One of the things that a `dirent` struct contains is the inode of the file.  It seemed to me that I should be able to directly grab all the information I needed straight out of the inode.  I went looking for an equivalent to `lstat` that took an inode, but couldn't find one.  So, I made one.  Simple enough.  Then I realized I had a problem:  FAT32 doesn't have true "inodes" so I had used the starting cluster of the file.  This in no way allowed me to find the information I needed.  So, I changed what I used as the inode value to be the position of the file's entry location within the directory.  THAT got me what I needed and the `istat` call I made was much faster than the duplicate allocate + lookup way of doing it with `lstat`.

It was still pretty slow, though.  Listing a directory with 15 entries was taking a little over 5 seconds.  I've got a couple of 86Box instances that I run for comparison and that speed was roughly on par with what an 8088 ran at with the `dir` command.  The eZ80 board I have should be running closer to what a 12 MHz 286 ran at.  Now, to be fair, `ls` does quite a bit more work than `dir` does and I'm using *almost* all POSIX calls here where `dir` has the luxury of making whatever arbitrary calls it wants to get the job done.  Still, I wasn't happy with this and wanted to improve the speed.

My suspicion was that the extra time was being sent polling from the UART.  I still hadn't gotten to the point of being able to put the console into a blocking state and only wake it when there was data to process, so it was still waking up and polling every UART port it owned every loop the scheduler made.  Due to the architecture of the Arduinos, I wasn't able to use interrupts on that platform, so it never made any sense to develop that capability.  Now, I needed it badly.

So, I started working on that.  I obviously needed a solution for the eZ80, but I also needed to be able to test this in software.  So, I needed a solution for the simulation/test harness environment as well.  Basically, the flow looks like this:
- A user presses a key
  - On POSIX, that unblocks a `read` call on a dedicated thread
  - On the eZ80, that triggers an interrupt
- The character is read in and written to a small buffer (of 16 characters, I think)
- A Boolean value is set to `true` to indicate that there's data for the port
- A Boolean value is set to `true` to indicate that there's data available at all
- The handler goes back to waiting for a character
  - On POSIX, this triggers the next `read` call
  - On the eZ80, the handler exits via a `RETI` instruction
- The process continues
- At the end of the scheduler's current iteration, it calls a HAL function that checks to see if there's any data that's come in
  - If there isn't, the function returns immediately
- The function clears the global Boolean
- The function iterates over each of the UARTs
- For each UART that has data
  - It clears the Boolean
  - It sends a message to the Console process that there's data to read
    - This causes the Console process to be put back on its ready queue if it wasn't already there
- The Console process wakes up and receives the message on its next iteration
  - It uses the new UART read function in the HAL to retrieve the data instead of polling it
- The Console process handles the incoming data

Needless to say, this was all a lot of work and it took me the better part of two (2) weeks to do everything.  But when I finally got everything put together, I discovered that I was absolutely right about the Console polling having been consuming a lot of the processor.  Listing that same 15-entry directory on the eZ80 now took about 2 seconds, so less than half the time that it had taken previously.  This is much closer to the 286-like performance I was hoping for.

The great thing about this performance enhancement, though, is that it's not the only one I can make.  I've got some ideas about how I can cache overlays on the eZ80 board so that I can make swapping them even faster.  If I'm right, that should improve things a lot, too.  I know the system is spending a lot of time loading overlays, if only for the initial part of a command's `main` function.
