# xx-Xxx-2026 - Agon Light 2 eZ80 Port

"Tell me lies, tell me sweet little lies..."
*- Fleetword Mac, "Little Lies"*

I mean, I guess if you write operating systems as a hobby, you have to already have a certain amount of, "If you want something done right, you have to do it yourself," in you.  This effort has taken that to an extreme, though.  I knew going into this that there was a certain amount of risk here.  The eZ80 is not a very popular chip and the toolchains that exist aren't very well supported.  I knew it was possible that I would run into situations where things I normally do wouldn't be supported and would require some rework from me, but I wasn't prepared for the way in which I would find that out.

First, to set the scene, my plan for this effort was to do it in stages.  [A few updates ago](2026-07-05_Scalability.md), I had restored the ability to build the OS with a built-in shell.  I started with that kind of setup for a few reasons.  First, obviously, it's very simple.  More precisely, though, the only hardware that that setup requires is a single serial port.  Several months ago, I wrote a simple MOS program for the Agon Light 2 that proved to me that I could use UART1 for my own purposes.  (MOS, the bulit-in OS/firmware, uses UART0 as a dedicated bus to the video processor on this board.)  Also, a few weeks ago, I had created a makefile for this target that would allow me to run NanoOs as a MOS application, so I didn't have to do any funky loading of my OS onto the chip's built-in flash and risk bricking the board.  A simple power cycle would recover from anything.

When I made the MOS program that used UART1, I went ahead and archived the necessary assembly functionality to interact with both UART0 and UART1.  So, all the low-level code existed and my stubbed-out HAL existed, I really just had to connect the two.  This was pretty straightforward.  The hardest part about this was organizing the function pointers and establishing naming conventions to be used for the assembly functions and files since I previously had no external assembly in my HAL code.

Getting the OS to launch as a MOS application took some debugging.  While my makefile had organized the code for that purpose correctly, it turned out that MOS expects some magic bytes to exist near the beginning of the binary.  Thank goodness I had Claude for that one.  Even with it, that took a while to debug and iron out.  Once I got the magic in place, I was able to launch NanoOs as a MOS application!!  ...and immediately hang the system.

That took some debugging and I'm glad I had Claude to help with this for two reasons:  (1) I'm not very familiar with eZ80/Z80/8080 assembly yet and (2) the bugs were ultimately Claude's fault.  I had used Claude to put together a **VERY** rudimentary bootloader for the eZ80.  It turned out that there was a bug in its implementation of loading the .bss section in RAM.  For anyone who's not familiar with that, that's a portion of program memory that has to be zeroed at program launch before any logic runs.  The way it had written the code, it was overwriting the register it was using to hold the value of `0` and was therefore just writing garbage to that section.  I'm a little smug about this because, even though I was using Claude to assist me in debugging, I was the one who landed on the possibility of memory being corrupted and who thought to check the loop in boot.asm.  Take *that* AI overlords!!

Once that problem was solved, I was able to launch NanoOs, see output on UART1, and login at the prompt!  HOORAY!!  OK!  Run the `help` command and *-REBOOT-*  Wait, what?!  What on earth happened?????  This took longer to debug and this is where things started to get weird.

In addition to the standard C-like output functions (printf, fputs), I also have a few low-level functions that just write a single value to the first available serial port, which was UART1 in this case.  There are three of them:  `printString`, `printInt`, and `printHex`.  Both `printInt` and `printHex` ultimately flow through printString, which is the one call that chooses the serial port and interfaces directly with the HAL  (This will become important later.)  At one point in my debugging, I added a `printInt` call somewhere in my code.  That hung the system.

It took me an entire day to figure out what was going on and here comes the first rude awakening.  [Previously](2026-08-02_Saving-Space.md), I mentioned in passing that this system has 24-bit registers.  `sizeof(int)` in this toolchain returns `3`.  Irritating, but I didn't consider it a huge deal because the toolchain does still have support for 32-bit and 64-bit integers, it just manipulates them in software instead of native hardware instructions.  No biggie, right?  Wrong...  "Support" here is misleading at best.  Like most programmers, I'm lazy.  I didn't want to have `printInt32` and `printInt64`, so my one `printInt` function takes a `long long` which is supposed to be a 64-bit type on this platform.  And, it is!  You can totally pass an integer value to the function and the compiler will dutifully promote it to a 64-bit value and store it that way on the stack.  Manipulating it, however...

My `printInt` and `printHex` functions perform math operations on the values to extract one digit at a time and fill a character buffer that gets passed to printString.  Pretty standard procedure.  I'd used printHex, which takes an `unsigned long long` integer, before and it worked just fine.  That function just does bit shifts and bitwise-AND operations which seem to work perfectly.  `printInt`, however, uses integer division and modulo.  This does not seem to work.  When I tried to run my function, the system hung.

I had to use Claude to debug this and it took a while.  It required digging into the assembly dumps for printInt to see what in the world was going on.  I don't fully understand the answer.  Apparently, the functions for doing 64-bit division in software were being inlined into my function and - for reasons I don't understand - that was consuming an enormous amount of stack space.  I guess on a system with gigs of memory and virtually unlimited stack space, consuming a few hundred extra bytes of stack is no big deal.  This system has 520 KB of RAM and right now my stacks are only 1 KB in size.  Consuming a few hundred extra bytes is a very big deal.  The compiler authors should have known better on this one.

Without me asking, when Claude finally "understood" the issue, it put in a "fix" that stripped out the processing for the upper 32 bits into a separate function that doesn't get linked in when the value passed in is under 32 bits, which it almost always is.  This, to me, was a completely unacceptable fix that I would have to address.  More on that later.  At that point in time, it allowed me to make progress on the reboot issue again, which I still needed to resolve.  So, I shelved the proper fix work for later.

Getting the `printInt` call to work allowed me to put low-level debug prints in my code to see what was going on.  I eventually narrowed it down to resuming a coroutine during the handling for `execve`.  Not good.  The Coroutines library I have is the very lowest level of the system and is exceedingly complex.  It's been very stable for a long time now and I try to do as little with it as possible.  The fact that it was happening during a resume was the worst possible place for it to be.  Resume works by a pair of `setjmp`/`longjmp` calls, which is nasty stuff.  Claude was absolutely no help here and I knew it would be.  This kind of logic is pretty eccentric and chatbots do poorly with things they haven't seen much - or any - of.

So, I started peppering my code with various print statements.  Here, I kind of shot myself in the foot for a while.  When I restored the ability to run with a built-in shell, I also transitioned NanoOs to be a capabilites-based OS.  One of the areas I added capabilities to was the HAL.  Almost everything in the HAL is capabilities-based now.  That includes UART operations.  The HAL verifies capabilites according to what process is currently running and here I am debugging the process of changing what process is currently running.  Once I got past the point in the procedure where the process that's reported as active changed, all output halted.  D'Oh!!  Took me a while to figure that one out.  Once I got past that point, then, FINALLY, at long last, I could see what was going on... and I didn't like what I found.
